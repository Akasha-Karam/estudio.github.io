1. Android

1.1 ¿Qué es Android?

Android es el sistema operativo móvil más usado del mundo, basado en Linux y propiedad de Google. Las apps Android se programan principalmente en Kotlin (lenguaje moderno y conciso) o en Java. Cada app se distribuye como un paquete .apk que se instala en el dispositivo.

Idea clave

Una app Android es un conjunto de pantallas (Activities y Fragments) conectadas entre sí, que reaccionan a eventos del usuario y muestran datos guardados en memoria, en disco o en un servidor remoto.

1.2 Android Studio

Android Studio es el IDE oficial de Google para desarrollar apps Android. Incluye:

  • Editor de código con autocompletado Kotlin/Java.
  • Editor visual de layouts XML.
  • Emulador: dispositivos virtuales para probar sin móvil físico.
  • Gradle: sistema de compilación y dependencias.
  • Logcat, profiler y herramientas de debug.

1.3 Estructura de un proyecto

Un proyecto Android tiene siempre esta estructura básica:

app/
app/
├── src/main/
│   ├── java/com/ejemplo/miapp/    ← código Kotlin
│   ├── res/
│   │   ├── layout/                 ← XML de pantallas (activity_main.xml…)
│   │   ├── drawable/               ← imágenes, iconos
│   │   ├── values/                 ← colores, strings, estilos
│   │   └── mipmap/                 ← icono de la app
│   └── AndroidManifest.xml         ← declaración de Activities/permisos
├── build.gradle                    ← dependencias del módulo
└── ...

1.4 build.gradle

Es el fichero de configuración. Aquí se declaran las dependencias y se activan funcionalidades como ViewBinding:

app/build.gradle.kts
android {
    namespace = "com.estudio.miapp"
    compileSdk = 34

    defaultConfig {
        applicationId = "com.estudio.miapp"
        minSdk = 24
        targetSdk = 34
    }

    buildFeatures {
        viewBinding = true            // ← activamos ViewBinding
    }
}

dependencies {
    implementation("androidx.core:core-ktx:1.12.0")
    implementation("androidx.appcompat:appcompat:1.6.1")
    implementation("com.google.android.material:material:1.10.0")
    implementation("androidx.fragment:fragment-ktx:1.6.2")
    implementation("androidx.lifecycle:lifecycle-viewmodel-ktx:2.6.2")
    implementation("androidx.lifecycle:lifecycle-livedata-ktx:2.6.2")
}
minSdk vs targetSdk

minSdk = versión más antigua de Android soportada. targetSdk = versión para la que la app está optimizada. Cuanto menor sea minSdk, más usuarios pueden instalar la app, pero menos APIs modernas puedes usar.

2. Activities y Fragments

Son las dos clases que representan las pantallas de una app Android.

2.1 Activities

Una Activity es una pantalla completa de tu app. Cada Activity tiene un ciclo de vida que Android gestiona:

MétodoCuándo se llama
onCreate()Al crear la Activity (configura layout, vistas, listeners).
onStart()La Activity pasa a ser visible.
onResume()La Activity está en primer plano e interactúa con el usuario.
onPause()Otra ventana queda encima (pausa lo que consume recursos).
onStop()Ya no es visible.
onDestroy()Se destruye (libera recursos).

Ejemplo: MainActivity

MainActivity.kt
package com.estudio.miapp

import android.os.Bundle
import androidx.appcompat.app.AppCompatActivity
import com.estudio.miapp.databinding.ActivityMainBinding

class MainActivity : AppCompatActivity() {

    private lateinit var binding: ActivityMainBinding

    override fun onCreate(savedInstanceState: Bundle?) {
        super.onCreate(savedInstanceState)

        // Inflar layout con ViewBinding
        binding = ActivityMainBinding.inflate(layoutInflater)
        setContentView(binding.root)

        // Acceder a las vistas
        binding.btnLogin.setOnClickListener {
            binding.txtSaludo.text = "¡Hola Android!"
        }
    }
}

2.2 Fragments

Un Fragment es un componente reutilizable de UI que representa una parte de una pantalla dentro de una Activity. Tiene su propio ciclo de vida.

Ventajas frente a las Activities

  • Reutilizable: el mismo Fragment en varias Activities.
  • Adaptable: layouts distintos para móvil y tablet.
  • Modular: dividir UI en piezas independientes.
  • Piénsalos como "sub-activities" con su propio ciclo de vida.

Ciclo de vida del Fragment

MétodoPara qué
onCreate()Setup inicial (sin tocar vistas).
onCreateView()Inflar el layout y devolver la View.
onViewCreated()Configurar vistas y listeners (la View ya existe).
onDestroyView()Libera la View (¡pero el Fragment puede seguir vivo!).

Ejemplo: HomeFragment

HomeFragment.kt
class HomeFragment : Fragment() {

    private var _binding: FragmentHomeBinding? = null
    private val binding get() = _binding!!

    override fun onCreateView(
        inflater: LayoutInflater,
        container: ViewGroup?,
        savedInstanceState: Bundle?
    ): View {
        _binding = FragmentHomeBinding.inflate(inflater, container, false)
        return binding.root
    }

    override fun onViewCreated(view: View, savedInstanceState: Bundle?) {
        super.onViewCreated(view, savedInstanceState)
        binding.txtTitle.text = "Inicio"
    }

    override fun onDestroyView() {
        super.onDestroyView()
        _binding = null   // evitar memory leaks
    }
}
¿Por qué _binding nullable?

La View del Fragment puede destruirse mientras el Fragment sigue vivo (por ejemplo, al hacer back stack). Por eso usamos _binding nullable y lo ponemos a null en onDestroyView(). La propiedad binding (sin guion bajo) lanza error si se accede después de destruir la vista.

2.3 Comunicación entre Fragments

Hay tres formas principales:

  1. Acceso directo: requireActivity() para llegar a la Activity padre.
  2. Callbacks (interfaces): el Fragment define una interfaz que la Activity implementa.
  3. ViewModel compartido: la forma moderna y recomendada (lo veremos en la sección 6).

3. Layouts y UI

3.1 Tipos de Layouts

Un Layout es un contenedor que organiza vistas en la pantalla. Los más importantes son:

LayoutPara qué sirve
LinearLayoutColoca elementos en línea vertical u horizontal.
ConstraintLayoutEl moderno y flexible. Posiciona por restricciones (recomendado).
FrameLayoutApila vistas una encima de otra.
RelativeLayoutAntiguo. Cada vista se posiciona relativa a otra (en desuso).

<LinearLayout xmlns:android="http://schemas.android.com/apk/res/android"
    android:layout_width="match_parent"
    android:layout_height="match_parent"
    android:orientation="vertical"
    android:padding="16dp">

    <TextView
        android:id="@+id/txtTitle"
        android:layout_width="wrap_content"
        android:layout_height="wrap_content"
        android:text="Login"
        android:textSize="24sp" />

    <EditText
        android:id="@+id/edtUser"
        android:layout_width="match_parent"
        android:layout_height="wrap_content"
        android:hint="Usuario" />

    <Button
        android:id="@+id/btnLogin"
        android:layout_width="match_parent"
        android:layout_height="wrap_content"
        android:text="Entrar" />

</LinearLayout>

3.2 ConstraintLayout

Es el layout recomendado hoy en día. Las vistas se posicionan con restricciones (constraints) respecto al padre o a otras vistas:

res/layout/activity_main.xml (ConstraintLayout)
<androidx.constraintlayout.widget.ConstraintLayout
    xmlns:android="http://schemas.android.com/apk/res/android"
    xmlns:app="http://schemas.android.com/apk/res-auto"
    android:layout_width="match_parent"
    android:layout_height="match_parent">

    <Button
        android:id="@+id/btnLogin"
        android:layout_width="wrap_content"
        android:layout_height="wrap_content"
        android:text="Entrar"
        app:layout_constraintTop_toTopOf="parent"
        app:layout_constraintStart_toStartOf="parent"
        app:layout_constraintEnd_toEndOf="parent"
        app:layout_constraintBottom_toBottomOf="parent" />

</androidx.constraintlayout.widget.ConstraintLayout>

Las restricciones top/bottom/start/end aplicadas a la vez centran el botón en pantalla.

3.3 ViewBinding

ViewBinding permite acceder a los elementos del XML directamente, sin findViewById(). Para cada layout, Android genera automáticamente una clase con el nombre del layout + "Binding" (ej: activity_main.xml → ActivityMainBinding).

Activación

app/build.gradle.kts
android {
    buildFeatures {
        viewBinding = true
    }
}

Uso en Activity

MainActivity.kt
private lateinit var binding: ActivityMainBinding

override fun onCreate(savedInstanceState: Bundle?) {
    super.onCreate(savedInstanceState)
    binding = ActivityMainBinding.inflate(layoutInflater)
    setContentView(binding.root)

    binding.txtTitle.text = "Login"
    binding.btnLogin.setOnClickListener { doLogin() }
}

Uso en Fragment

HomeFragment.kt
private var _binding: FragmentHomeBinding? = null
private val binding get() = _binding!!

override fun onCreateView(
    inflater: LayoutInflater,
    container: ViewGroup?,
    savedInstanceState: Bundle?
): View {
    _binding = FragmentHomeBinding.inflate(inflater, container, false)
    return binding.root
}

override fun onDestroyView() {
    super.onDestroyView()
    _binding = null
}
Ventajas de ViewBinding
  • Null safety: el binding nunca da NullPointerException por una vista que no exista.
  • Type safety: cada vista tiene su tipo correcto (TextView, Button…), sin casteos.
  • Rápido: el código se genera en tiempo de compilación.

4. RecyclerView

El RecyclerView es el componente para mostrar listas o grids de elementos. Recicla las vistas cuando se hace scroll, lo que lo hace muy eficiente incluso con miles de elementos. Reemplaza al antiguo ListView.

Un RecyclerView tiene cuatro piezas:

  1. Modelo de datos (data class) — qué se va a mostrar.
  2. ViewHolder — referencia a las vistas de cada fila.
  3. Adapter — conecta los datos con las vistas.
  4. LayoutManager — cómo se disponen los elementos (vertical, grid…).

4.1 Modelo de datos

model/Task.kt
data class Task(
    val id: Int,
    val title: String,
    val points: Int
)

4.2 Adapter + ViewHolder

El Adapter implementa tres métodos esenciales:

MétodoPara qué
onCreateViewHolder()Crea una nueva fila (infla el XML).
getItemCount()Cuántos elementos hay en total.
onBindViewHolder()Pinta los datos de la posición n en el ViewHolder.
adapter/TasksAdapter.kt
class TasksAdapter(
    private var tasks: List<Task>,
    private val onClick: (Task) -> Unit
) : RecyclerView.Adapter<TasksAdapter.TaskViewHolder>() {

    inner class TaskViewHolder(
        private val binding: ItemTaskBinding
    ) : RecyclerView.ViewHolder(binding.root) {

        fun bind(task: Task) {
            binding.txtTitle.text  = task.title
            binding.txtPoints.text = task.points.toString()
            binding.root.setOnClickListener { onClick(task) }
        }
    }

    override fun onCreateViewHolder(parent: ViewGroup, viewType: Int): TaskViewHolder {
        val binding = ItemTaskBinding.inflate(
            LayoutInflater.from(parent.context), parent, false)
        return TaskViewHolder(binding)
    }

    override fun getItemCount() = tasks.size

    override fun onBindViewHolder(holder: TaskViewHolder, position: Int) {
        holder.bind(tasks[position])
    }

    fun updateTasks(newTasks: List<Task>) {
        tasks = newTasks
        notifyDataSetChanged()
    }
}

4.3 Uso en la Activity / Fragment

HomeFragment.kt
override fun onViewCreated(view: View, savedInstanceState: Bundle?) {
    super.onViewCreated(view, savedInstanceState)

    val adapter = TasksAdapter(
        tasks = listOf(
            Task(1, "Estudiar Android", 5),
            Task(2, "Hacer ejercicios", 3)
        ),
        onClick = { t -> Log.d("Tasks", "Clicked: ${t.title}") }
    )

    binding.recyclerView.layoutManager = LinearLayoutManager(requireContext())
    binding.recyclerView.adapter       = adapter
}
LayoutManager
  • LinearLayoutManager → lista vertical (más común) u horizontal.
  • GridLayoutManager(ctx, columnas) → cuadrícula.
  • StaggeredGridLayoutManager → cuadrícula tipo Pinterest.

5. Diálogos

Un diálogo es una ventana pequeña que aparece encima de la pantalla para pedir información, confirmar una acción o mostrar un mensaje.

5.1 AlertDialog

La forma más rápida. Útil para mensajes simples de confirmación.

borrarTarea()
AlertDialog.Builder(requireContext())
    .setTitle("Borrar tarea")
    .setMessage("¿Seguro que quieres borrar esta tarea?")
    .setPositiveButton("Sí") { _, _ ->
        viewModel.borrarTarea(task)
    }
    .setNegativeButton("Cancelar", null)
    .show()

5.2 DialogFragment

Para diálogos más complejos (con varios campos de entrada, validación, etc.) se usa DialogFragment: una subclase de Fragment que se muestra como diálogo y tiene su propio ciclo de vida.

Ventajas frente a AlertDialog:

  • Sobrevive a rotaciones de pantalla.
  • Puedes tener layouts personalizados con XML.
  • Se integra de forma natural con ViewModel (ver sección 7).
ui/dialogs/AfegirTascaDialog.kt
class AfegirTascaDialog : DialogFragment() {

}

6. Arquitectura MVVM

La arquitectura MVVM (Model-View-ViewModel) separa la app en tres capas para que cada una tenga una sola responsabilidad:

CapaResponsabilidadQuién es
ModelLos datos y la lógica de negocio.Data classes, repositorios.
ViewMostrar datos y reaccionar a clicks.Activity, Fragment, XML.
ViewModelPuente entre Model y View. Guarda estado.Una clase que extiende ViewModel.

6.1 ViewModel

El ViewModel guarda y gestiona los datos relacionados con la UI de forma consciente del ciclo de vida. La lógica y los datos quedan separados de la UI (Activity/Fragment).

Características clave

  • Separación: lógica independiente de la UI.
  • Testeable: sin dependencias de Android.
  • Reutilización: varios Fragments comparten el mismo ViewModel.
  • Persistencia: sobrevive a las rotaciones de pantalla.
viewmodel/TasksViewModel.kt
class TasksViewModel : ViewModel() {

    private val _tasks = MutableLiveData<List<Task>>(emptyList())
    val tasks: LiveData<List<Task>> = _tasks

    fun addTask(title: String, points: Int) {
        val newTask = Task(id = (_tasks.value?.size ?: 0) + 1, title, points)
        _tasks.value = _tasks.value.orEmpty() + newTask
    }

    fun deleteTask(task: Task) {
        _tasks.value = _tasks.value.orEmpty().filterNot { it.id == task.id }
    }
}

Acceso desde Activity/Fragment

SintaxisÁmbitoUso
by viewModels() Local al Fragment/Activity Cada pantalla tiene su propia instancia.
by activityViewModels() Compartido en la Activity Varios Fragments acceden a la misma instancia. 
// Fragment con su propio ViewModel
private val viewModel: TasksViewModel by viewModels()

// Fragment con ViewModel compartido (común con DialogFragment)
private val viewModel: TasksViewModel by activityViewModels()

6.2 LiveData

LiveData es una clase contenedora de datos observable que forma parte de Android Jetpack. La UI se "suscribe" y se actualiza automáticamente cuando los datos cambian.

Características

  • Observable: notifica a sus observadores cuando cambia.
  • Consciente del ciclo de vida: solo notifica si la UI está activa (STARTED/RESUMED). Sin memory leaks.
  • Limpieza automática: cuando la View se destruye, se desuscribe sola.

LiveData vs MutableLiveData

TipoPermite modificarDónde se usa
LiveDataNo (solo lectura)Expuesta al exterior
MutableLiveDataSí (setValue, postValue)Privada dentro del ViewModel
Patrón recomendado
private val _data = MutableLiveData<String>()   // privada, mutable
val data: LiveData<String> = _data              // pública, de solo lectura

6.3 Patrón Observer

Desde el Fragment/Activity, observamos los cambios de LiveData con .observe():

viewModel.tasks.observe(viewLifecycleOwner) { tasks ->
    // Se ejecuta cada vez que la lista cambia
    adapter.updateTasks(tasks)
}
setValue vs postValue
  • setValue(x): solo desde el hilo principal.
  • postValue(x): se puede llamar desde cualquier hilo (lo encola para el hilo principal).

app/src/main/java/com/estudio/tasques/
app/

├── model/            ← Task.kt
├── viewmodel/        ← TasksViewModel.kt
├── ui/fragments/     ← HomeFragment.kt
├── ui/dialogs/       ← AfegirTascaDialog.kt
└── adapter/          ← TasksAdapter.kt

7.2 Model

model/Task.kt
@Parcelize
data class Task(
    val id:     Int,
    val title:  String,
    val points: Int,
    val data:   String
) : Parcelable

@Parcelize permite pasar el objeto entre Activities/Fragments (requiere el plugin kotlin-parcelize en build.gradle).

7.3 ViewModel con eventos

viewmodel/TasksViewModel.kt
enum class TaskAction { AFEGIDA, MODIFICADA, ELIMINADA, NONE }

class TasksViewModel : ViewModel() {

    // Evento: qué acaba de pasar
    private val _action = MutableLiveData(TaskAction.NONE)
    val action: LiveData<TaskAction> = _action

    // Evento de error (null si no hay error)
    private val _error = MutableLiveData<String?>(null)
    val error: LiveData<String?> = _error

    fun addTask(title: String, points: Int, data: String) {
        if (title.isBlank()) {
            _error.value = "El título no puede estar vacío"
            return
        }
        if (points <= 0) {
            _error.value = "Los puntos deben ser positivos"
            return
        }

        val nueva = Task(
            id     = TasksList.tasks.size + 1,
            title  = title,
            points = points,
            data   = data
        )
        TasksList.tasks.add(nueva)
        _action.value = TaskAction.AFEGIDA
    }

    fun deleteTask(task: Task) {
        TasksList.tasks.remove(task)
        _action.value = TaskAction.ELIMINADA
    }
}

7.4 DialogFragment

ui/dialogs/AfegirTascaDialog.kt
class AfegirTascaDialog : DialogFragment() {

    // ViewModel COMPARTIDO con la Activity → con el HomeFragment
    private val viewModel: TasksViewModel by activityViewModels()

    private var _binding: DialogAfegirTascaBinding? = null
    private val binding get() = _binding!!

    override fun onCreateView(
        inflater: LayoutInflater,
        container: ViewGroup?,
        savedInstanceState: Bundle?
    ): View {
        _binding = DialogAfegirTascaBinding.inflate(inflater, container, false)
        return binding.root
    }

    override fun onViewCreated(view: View, savedInstanceState: Bundle?) {
        super.onViewCreated(view, savedInstanceState)

        // Observa errores del ViewModel para mostrarlos en el diálogo
        viewModel.error.observe(viewLifecycleOwner) { msg ->
            if (msg != null) {
                Toast.makeText(requireContext(), msg, Toast.LENGTH_SHORT).show()
            }
        }

        binding.btnGuardar.setOnClickListener {
            val title  = binding.edtTitle.text.toString()
            val points = binding.edtPoints.text.toString().toIntOrNull() ?: 0
            val data   = binding.edtData.text.toString()

            viewModel.addTask(title, points, data)
            dismiss()
        }

        binding.btnCancelar.setOnClickListener { dismiss() }
    }

    override fun onDestroyView() {
        super.onDestroyView()
        _binding = null
    }
}

7.5 Fragment principal

ui/fragments/HomeFragment.kt
class HomeFragment : Fragment() {

    private val viewModel: TasksViewModel by activityViewModels()
    private lateinit var adapter: TasksAdapter

    private var _binding: FragmentHomeBinding? = null
    private val binding get() = _binding!!

    override fun onCreateView(
        inflater: LayoutInflater,
        container: ViewGroup?,
        savedInstanceState: Bundle?
    ): View {
        _binding = FragmentHomeBinding.inflate(inflater, container, false)
        return binding.root
    }

    override fun onViewCreated(view: View, savedInstanceState: Bundle?) {
        super.onViewCreated(view, savedInstanceState)

        // 1. Configurar RecyclerView
        adapter = TasksAdapter(TasksList.tasks) { task ->
            viewModel.deleteTask(task)
        }
        binding.recyclerView.layoutManager = LinearLayoutManager(requireContext())
        binding.recyclerView.adapter       = adapter

        // 2. Observar eventos del ViewModel
        viewModel.action.observe(viewLifecycleOwner) { action ->
            when (action) {
                TaskAction.AFEGIDA, TaskAction.ELIMINADA ->
                    adapter.updateTasks(TasksList.tasks)
                else -> { /* nada */ }
            }
        }

        // 3. Botón para abrir el diálogo de añadir
        binding.fabAdd.setOnClickListener {
            AfegirTascaDialog().show(parentFragmentManager, "afegir")
        }
    }

    override fun onDestroyView() {
        super.onDestroyView()
        _binding = null
    }
}
¿Por qué activityViewModels()?

Porque queremos que el mismo ViewModel sea visible desde el HomeFragment y desde el AfegirTascaDialog. Si usáramos viewModels(), cada Fragment tendría una instancia distinta y no se enterarían de los cambios del otro.

Flujo completo

  1. Usuario pulsa el FAB → HomeFragment abre AfegirTascaDialog.
  2. El diálogo llena los campos y pulsa Guardar.
  3. El diálogo llama a viewModel.addTask(...).
  4. El ViewModel valida, añade a TasksList y dispara _action.value = AFEGIDA.
  5. HomeFragment tenía un observe sobre action → refresca el RecyclerView.
  6. El diálogo se cierra con dismiss().

Ejercicio 1 — ViewBinding en una Activity

Crea una Activity con un TextView y un Button. Al pulsar el botón, cambia el texto del TextView por "¡Has hecho clic!". Usa ViewBinding (sin findViewById).

Ver solución

<LinearLayout xmlns:android="http://schemas.android.com/apk/res/android"
    android:layout_width="match_parent"
    android:layout_height="match_parent"
    android:orientation="vertical"
    android:padding="24dp">

    <TextView

        holder.bind(productos[position])

    override fun getItemCount() = productos.size
}

Ejercicio 3 — Contador con ViewModel + LiveData

Crea un ViewModel con un contador. La Activity debe tener dos botones (+ y −) y un TextView. Cada vez que se pulsa un botón, el ViewModel actualiza el contador y el TextView se refresca automáticamente via LiveData. El contador debe sobrevivir a las rotaciones de pantalla.

Ver solución
CounterViewModel.kt
class CounterViewModel : ViewModel() {
    private val _count = MutableLiveData(0)
    val count: LiveData<Int> = _count

    fun increment() { _count.value = (_count.value ?: 0) + 1 }
    fun decrement() { _count.value = (_count.value ?: 0) - 1 }
}
MainActivity.kt
class MainActivity : AppCompatActivity() {

    private lateinit var binding: ActivityMainBinding
    private val viewModel: CounterViewModel by viewModels()

    override fun onCreate(savedInstanceState: Bundle?) {
        super.onCreate(savedInstanceState)
        binding = ActivityMainBinding.inflate(layoutInflater)
        setContentView(binding.root)

        // El TextView se actualiza solo cuando el contador cambia
        viewModel.count.observe(this) { n ->
            binding.txtCount.text = n.toString()
        }

        binding.btnPlus.setOnClickListener  { viewModel.increment() }
        binding.btnMinus.setOnClickListener { viewModel.decrement() }
    }
}

NombresViewModel.kt
class NombresViewModel : ViewModel() {
    private val _nombres = MutableLiveData<List<String>>(emptyList())

    fun add(nombre: String) {
        if (nombre.isNotBlank()) {

        }
    }

Las 5 reglas de oro de Android
  1. Usa ViewBinding en lugar de findViewById.
  2. En Fragments, pon _binding = null en onDestroyView() para evitar memory leaks.
  3. La lógica va en el ViewModel, no en la Activity ni en el Fragment. La UI solo pinta.
  4. Para compartir datos entre Fragments y diálogos, usa by activityViewModels().
  5. Observa LiveData con viewLifecycleOwner en Fragments (no con this) para evitar crashes tras rotar.
¿Y ahora qué?

Cuando domines MVVM con ViewModel + LiveData, prueba:

  • Coroutines y Flow para operaciones asíncronas.
  • Room para guardar datos localmente.
  • Retrofit para consumir tu propio backend (¡los apuntes de Spring Boot te enseñan a crearlo!).
  • Jetpack Compose para hacer UIs declarativas, sin XML.
