1. Spring Boot

1.1 ¿Qué es Spring Boot?

Spring Boot es un framework de Java pensado para construir aplicaciones web (especialmente APIs REST) de forma rápida y con muy poca configuración. Imagina que Spring "normal" te pide montar tú mismo todas las piezas (servidor, conexión a base de datos, seguridad…). Spring Boot ya viene con todas esas piezas ensambladas: tú te dedicas solo a la lógica.

Sus principales características son:

  • Servidor incrustado (Tomcat / Jetty): no necesitas instalarlo aparte.
  • Auto-configuración: detecta las librerías añadidas y las configura sola.
  • Starters: dependencias agrupadas (spring-boot-starter-web, spring-boot-starter-data-jpa…) que añaden todo lo necesario para una funcionalidad.
  • Anotaciones en lugar de XML: @RestController, @Service, @Entity…
  • Listo para producción: métricas, health-checks y logs incluidos.
Idea clave

Spring Boot = Spring + configuración automática + servidor incrustado. Tu proyecto se empaqueta como un .jar ejecutable: con java -jar mi-app.jar ya está corriendo.

1.2 Crear el proyecto

La forma más fácil es usar Spring Initializr, una web que genera el esqueleto del proyecto.

  1. Entra en start.spring.io.
  2. Selecciona: Maven, Java 17, Spring Boot 3.2.x.
  3. Group: com.estudio, Artifact: demo.
  4. Añade dependencias:
    • Spring Web — para crear APIs REST.
    • Spring Data JPA — para acceso a base de datos.
    • MySQL Driver — para conectarse a MySQL.
    • Spring Security — para la parte de JWT.
    • Lombok — para evitar código repetitivo.
    • Validation — para validar datos de entrada.
  5. Pulsa Generate, descomprime el .zip y ábrelo en IntelliJ o VS Code.

2. Spring JDBC

Spring JDBC es la primera capa de acceso a datos del ecosistema Spring. Te ofrece la clase JdbcTemplate, que simplifica enormemente el uso de JDBC puro de Java, pero aún escribes tú mismo el SQL.

Ventajas e inconvenientes

VentajasInconvenientes
  • Control total sobre el SQL.
  • Más rápido para consultas complejas.
  • Sin abstracciones "mágicas".
  • Escribes mucho código repetitivo (boilerplate).
  • No portable entre BDs (cada SGBD tiene su dialecto).
  • Tienes que mapear filas a objetos a mano.

Ejemplo

Una consulta con JdbcTemplate para listar libros:

repository/LibroJdbcRepository.java
@Repository
public class LibroJdbcRepository {

    private final JdbcTemplate jdbc;

    public LibroJdbcRepository(JdbcTemplate jdbc) {
        this.jdbc = jdbc;
    }

    public List<Libro> findAll() {
        String sql = "SELECT id, titulo, autor, anyo FROM libros";

        return jdbc.query(sql, (rs, row) -> new Libro(
                rs.getLong("id"),
                rs.getString("titulo"),
                rs.getString("autor"),
                rs.getInt("anyo")
        ));
    }

    public int insertar(Libro l) {
        return jdbc.update(
            "INSERT INTO libros (titulo, autor, anyo) VALUES (?, ?, ?)",
            l.getTitulo(), l.getAutor(), l.getAnyo()
        );
    }
}
En estos apuntes

A partir de ahora usaremos siempre Spring Data JPA en lugar de JDBC, porque es lo que se usa en proyectos modernos. Spring JDBC se queda como referencia para entender de dónde venimos.

3. Spring Data JPA

Spring Data JPA es una capa sobre Hibernate que permite hacer CRUD (Crear, Leer, Actualizar, Borrar) sin escribir SQL. Tú defines clases Java (entidades) y JPA se encarga de crear las tablas y traducir los métodos a SQL.

3.1 Entidades

Una entidad es una clase Java que representa una tabla. Cada atributo es una columna.

entity/Libro.java
package com.estudio.demo.entity;

import jakarta.persistence.*;
import lombok.*;

@Entity                              // ← es una entidad JPA
@Table(name = "libros")              // ← tabla "libros"
@Data
@NoArgsConstructor
@AllArgsConstructor
@Builder
public class Libro {

    @Id                                                       // clave primaria
    @GeneratedValue(strategy = GenerationType.IDENTITY)       // auto-incremental
    private Long id;

    @Column(nullable = false, length = 100)
    private String titulo;

    @Column(nullable = false)
    private String autor;

    private Integer anyo;
}

Al arrancar la aplicación, Hibernate ejecuta automáticamente:

CREATE TABLE libros (
    id     BIGINT       AUTO_INCREMENT PRIMARY KEY,
    titulo VARCHAR(100) NOT NULL,
    autor  VARCHAR(255) NOT NULL,
    anyo   INT
);

3.2 Repository

El repository es la interfaz que te permite acceder a la BD. Lo asombroso es que tú solo declaras la interfaz: ¡Spring escribe la implementación!

repository/LibroRepository.java
package com.estudio.demo.repository;

import com.estudio.demo.entity.Libro;
import org.springframework.data.jpa.repository.JpaRepository;
import java.util.List;

public interface LibroRepository extends JpaRepository<Libro, Long> {

    // Spring lee el nombre del método y genera la SQL automáticamente:
    List<Libro> findByAutor(String autor);
    // → SELECT * FROM libros WHERE autor = ?

    List<Libro> findByAnyoGreaterThan(int anyo);
    // → SELECT * FROM libros WHERE anyo > ?
}
Query derivation

Spring Data deriva la SQL del nombre del método: findByX, findByXAndY, existsByX, countByX… son automáticos.

Heredando de JpaRepository consigues gratis estos métodos:

MétodoQué hace
save(libro)INSERT o UPDATE
findById(id)SELECT por id
findAll()Devuelve todos
deleteById(id)DELETE por id
count()Cuenta filas
existsById(id)Comprueba si existe

3.3 Service

Para tener el código ordenado, separamos en capas:

  • Controller — recibe las peticiones HTTP.
  • Service — lógica de negocio (validaciones, reglas).
  • Repository — habla con la BD.
service/LibroService.java
@Service
@RequiredArgsConstructor
public class LibroService {

    private final LibroRepository repo;   // Spring lo inyecta solo

    public List<Libro> listar()              { return repo.findAll(); }
    public Libro      crear(Libro l)         { return repo.save(l); }
    public Libro      buscar(Long id)        { return repo.findById(id).orElseThrow(); }
    public void       borrar(Long id)        { repo.deleteById(id); }
}

3.4 Relaciones entre entidades

JPA permite expresar relaciones entre tablas con anotaciones:

AnotaciónSignificadoEjemplo
@OneToOneUno a unoEstudiante ↔ expediente
@OneToManyUno a muchosAutor → libros
@ManyToOneMuchos a unoLibro → autor
@ManyToManyMuchos a muchosLibros ↔ géneros

Ejemplo de relación @OneToMany / @ManyToOne

entity/Autor.java
@Entity
@Data
public class Autor {
    @Id @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;
    private String nombre;

    @OneToMany(mappedBy = "autor", cascade = CascadeType.ALL)
    private List<Libro> libros;
}
entity/Libro.java
@Entity
@Data
public class Libro {
    @Id @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;
    private String titulo;

    @ManyToOne
    @JoinColumn(name = "autor_id")     // crea la columna FK en la tabla libros
    private Autor autor;
}

4. API REST

Una API REST es una manera estándar de comunicar dos programas a través de HTTP. El cliente hace una petición a una URL y el servidor responde con datos en formato JSON.

REST significa Representational State Transfer: es un estilo de arquitectura donde cada recurso (libro, usuario, pedido…) tiene su URL, y los verbos HTTP indican qué quieres hacer.

4.1 Verbos HTTP

VerboSignificadoEjemplo
GETLeer datosGET /api/libros → lista libros
POSTCrear un recurso nuevoPOST /api/libros → añade un libro
PUTModificar uno existentePUT /api/libros/5 → actualiza el libro 5
DELETEBorrarDELETE /api/libros/5 → borra el libro 5

4.2 Códigos de estado

El servidor responde con un código numérico que indica si todo ha ido bien o no:

CódigoSignificado
200 OKTodo correcto
201 CreatedRecurso creado
204 No ContentOK pero sin datos en la respuesta
400 Bad RequestDatos enviados incorrectos
401 UnauthorizedFalta autenticarse
403 ForbiddenAutenticado pero sin permisos
404 Not FoundEl recurso no existe
500 Internal Server ErrorError en el servidor

4.3 Controllers

Los controllers son las clases que reciben las peticiones HTTP. Usan anotaciones que empiezan por @:

Ejemplo: Hola Mundo

controller/HolaController.java
package com.estudio.demo.controller;

import org.springframework.web.bind.annotation.*;

@RestController                      // ← clase que responde con JSON
@RequestMapping("/api")              // ← prefijo común para las URLs
public class HolaController {

    @GetMapping("/hola")             // ← GET /api/hola
    public String hola() {
        return "¡Hola desde Spring Boot!";
    }

    @GetMapping("/hola/{nombre}")    // ← variable en la URL
    public String holaPersonal(@PathVariable String nombre) {
        return "¡Hola, " + nombre + "!";
    }
}

Arrancando la app (./mvnw spring-boot:run) y abriendo http://localhost:8080/api/hola/Marta:

¡Hola, Marta!

Anotaciones del ejemplo

  • @RestController — marca la clase como controller que devuelve datos (no HTML).
  • @RequestMapping("/api") — prefijo común para todas las URLs de la clase.
  • @GetMapping("/hola") — este método responde al verbo GET en esa ruta.
  • @PathVariable — coge una parte de la URL y la mete en una variable.

Ejemplo: CRUD completo de libros

controller/LibroController.java
@RestController
@RequestMapping("/api/libros")
@RequiredArgsConstructor
public class LibroController {

    private final LibroService service;

    @GetMapping
    public List<Libro> listar() {
        return service.listar();
    }

    @GetMapping("/{id}")
    public Libro uno(@PathVariable Long id) {
        return service.buscar(id);
    }

    @PostMapping
    public ResponseEntity<Libro> crear(@RequestBody Libro l) {
        return ResponseEntity.status(HttpStatus.CREATED).body(service.crear(l));
    }

    @DeleteMapping("/{id}")
    public ResponseEntity<Void> borrar(@PathVariable Long id) {
        service.borrar(id);
        return ResponseEntity.noContent().build();
    }
}

¿Qué es JSON?

JSON es un formato de texto para representar datos: parejas "clave": valor entre llaves. Es lo que se manda y se recibe en una API REST.

5. DTOs y Mappers

Cómo convertimos entidades JPA en respuestas de API — y peticiones HTTP en objetos persistibles — sin mezclar capas ni exponer el esquema de la base de datos.

5.1 ¿Qué son los DTOs?

Un DTO (Data Transfer Object) es una clase Java sencilla —sin lógica de negocio— cuyo propósito es transportar datos entre capas. En una API REST distinguimos dos tipos:

TipoDescripciónEjemplos
Request DTO Representa el cuerpo de la petición HTTP entrante. Contiene los campos que el cliente puede enviar. StudentCreateRequest
Response DTO Representa la respuesta que la API devuelve al cliente. Se usa para controlar qué información se expone. StudentDTO
¿Por qué no devolver la entidad JPA directamente?

Las entidades JPA (@Entity) están acopladas a la base de datos: contienen anotaciones de persistencia, relaciones bidireccionales y, a menudo, campos que no queremos exponer (contraseñas, claves foráneas internas, etc.). Los DTOs permiten desacoplar lo que se guarda de lo que se envía o se recibe.

StudentDTO — Response

Se usa para devolver información de un estudiante al cliente. Incluye un campo academicRecord de tipo AcademicRecordDTO, que devuelve el expediente académico anidado en la misma respuesta.

dto/StudentDTO.java (Response DTO)
public class StudentDTO {
    private Long id;
    private String firstName;
    private String lastName;
    private String email;
    private AcademicRecordDTO academicRecord;   // DTO anidado, NO entidad JPA

    // Constructor sin academicRecord (para evitar recursividad)
    public StudentDTO(Long id, String firstName, String lastName, String email) { ... }

    // Getters y Setters
    public AcademicRecordDTO getAcademicRecord() { return academicRecord; }
    public void setAcademicRecord(AcademicRecordDTO ar) { this.academicRecord = ar; }
}

StudentCreateRequest — Request

Representa el JSON que envía el cliente para crear un estudiante. Permite crear estudiante y expediente en una sola llamada gracias a los campos opcionales recordNumber y recordStatus.

dto/StudentCreateRequest.java (Request DTO)
public class StudentCreateRequest {
    private String firstName;      // Obligatorio
    private String lastName;       // Obligatorio
    private String email;          // Obligatorio - debe ser único
    private String recordNumber;   // Opcional - si se envía, se crea el expediente
    private String recordStatus;   // Opcional - por defecto "ACTIVE"
    // Getters y Setters...
}

Ejemplo de JSON que envía el cliente:

POST /api/students
{
  "firstName":    "Anna",
  "lastName":     "Garcia",
  "email":        "anna.garcia@escola.cat",
  "recordNumber": "EXP-2024-001",
  "recordStatus": "ACTIVE"
}

5.2 ¿Qué son los Mappers?

Un Mapper es una clase de Spring (@Component) que se encarga de la conversión entre entidades y DTOs. Centraliza toda la lógica de transformación en un solo sitio, de manera que ni el service ni el controller tienen que saber cómo se construye un DTO.

MétodoEntradaSalidaQuién lo usa
toDto()Entidad JPAResponse DTOService (lectura y creación)
toEntity()Request DTOEntidad JPAService (creación y actualización)
mapper/StudentMapper.java
@Component   // Spring lo registra como bean inyectable
public class StudentMapper {

    // ── Entidad JPA → Response DTO ─────────────────────────────────
    public StudentDTO toDto(Student student) {
        if (student == null) return null;   // null-safe

        StudentDTO dto = new StudentDTO(
            student.getId(),
            student.getFirstName(),
            student.getLastName(),
            student.getEmail()
        );

        // Si el estudiante tiene expediente, lo convertimos a DTO anidado
        if (student.getAcademicRecord() != null) {
            AcademicRecordDTO record = new AcademicRecordDTO(
                student.getAcademicRecord().getId(),
                student.getAcademicRecord().getRecordNumber(),
                student.getAcademicRecord().getStatus()
                // NOTA: no añadimos student → evitamos referencia circular
            );
            dto.setAcademicRecord(record);
        }

        return dto;
    }

    // ── Request DTO → Entidad JPA ──────────────────────────────────
    public Student toEntity(StudentCreateRequest request) {
        if (request == null) return null;

        Student student = new Student(
            request.getFirstName(),
            request.getLastName(),
            request.getEmail()
        );

        // Creamos el expediente si el cliente envió el número
        if (request.getRecordNumber() != null) {
            AcademicRecord record = new AcademicRecord(
                request.getRecordNumber(),
                request.getRecordStatus() != null
                    ? request.getRecordStatus()
                    : "ACTIVE"   // valor por defecto
            );
            student.setAcademicRecord(record);
        }

        return student;
    }
}

Puntos clave del Mapper

  • Null-safety: ambos métodos comprueban null al inicio.
  • Creación en cascada: toEntity() puede crear un AcademicRecord asociado si el request lo incluye.
  • Evitar recursividad: cuando toDto() crea el AcademicRecordDTO anidado, no incluye de vuelta el estudiante, cortando el ciclo.
Referencia circular

Student tiene un AcademicRecord, y AcademicRecord tiene un Student. Si los dos DTOs se incluyeran mutuamente sin restricciones, el serializador JSON entraría en un bucle infinito. Los mappers lo resuelven construyendo el objeto anidado manualmente sin volver a incluir la referencia de vuelta.

5.3 Cómo afecta el Mapper al Service

Regla general del service

El service nunca construye DTOs ni entidades manualmente. Delega completamente al Mapper. Solo se ocupa de la lógica de negocio (validaciones, llamadas al repository, orquestación).

service/StudentService.java
@Service
public class StudentService {

    private final StudentRepository studentRepository;
    private final StudentMapper studentMapper;     // inyectado por constructor

    public StudentService(StudentRepository repo, StudentMapper mapper) {
        this.studentRepository = repo;
        this.studentMapper = mapper;
    }

    // ── Lectura por ID: mapper a la salida ────────────────────────
    public StudentDTO getStudentById(Long id) {
        Optional<Student> student = studentRepository.findById(id);
        if (student.isPresent()) {
            return studentMapper.toDto(student.get());   // Entidad → DTO
        }
        return null;
    }

    // ── Listar todos: mapper en bucle ─────────────────────────────
    public List<StudentDTO> getAllStudents() {
        List<Student> students = studentRepository.findAll();
        List<StudentDTO> dtos = new ArrayList<>();
        for (Student item : students) {
            dtos.add(studentMapper.toDto(item));
        }
        return dtos;
    }

    // ── Crear: mapper a la entrada Y a la salida ──────────────────
    public StudentDTO createStudent(StudentCreateRequest request) {
        if (studentRepository.existsByEmail(request.getEmail())) {
            throw new RuntimeException("El email ya existe: " + request.getEmail());
        }

        Student student = studentMapper.toEntity(request);          // Request → Entidad
        Student saved   = studentRepository.save(student);          // Guarda en BD
        return studentMapper.toDto(saved);                          // Entidad → DTO
    }
}
Dos usos del Mapper en createStudent

En createStudent el mapper se usa dos veces: primero para convertir el request en entidad (entrada), y después para convertir la entidad guardada en DTO (salida). Siempre se devuelve el DTO obtenido de la BD —no el request original— porque la BD puede añadir valores como el ID autogenerado.

5.4 Cómo afecta el Mapper al Controller

El controller no usa nunca el mapper directamente

El controller nunca llama al mapper. Trabaja exclusivamente con DTOs: recibe Request DTOs del cuerpo HTTP y devuelve Response DTOs al cliente. El impacto del mapper en el controller es indirecto: el controller debe declarar los tipos DTO correctos en sus métodos.

controller/StudentController.java
@RestController
@RequestMapping("/api/students")
public class StudentController {

    private final StudentService studentService;

    public StudentController(StudentService service) {
        this.studentService = service;
    }

    @PostMapping
    public ResponseEntity<StudentDTO> createStudent(
            @RequestBody StudentCreateRequest request) {       // ← Request DTO
        StudentDTO created = studentService.createStudent(request);
        return new ResponseEntity<>(created, HttpStatus.CREATED);
    }

    @GetMapping("/{id}")
    public ResponseEntity<StudentDTO> getStudentById(@PathVariable Long id) {
        return ResponseEntity.ok(studentService.getStudentById(id));
    }

    @GetMapping
    public ResponseEntity<List<StudentDTO>> getAllStudents() {
        return ResponseEntity.ok(studentService.getAllStudents());
    }
}
El repository nunca ve un DTO

El StudentRepository nunca recibe ni devuelve un DTO. Siempre trabaja exclusivamente con la entidad JPA Student. La conversión la hace el Mapper dentro del Service, no en el controller ni en el repository.

Flujo completo de datos (POST /api/students)

  1. Cliente envía JSON → StudentController lo recibe como StudentCreateRequest.
  2. Controller llama service.createStudent(request).
  3. Service llama mapper.toEntity(request) → obtiene una entidad Student.
  4. Service llama repository.save(student) → la BD guarda y devuelve la entidad con ID generado.
  5. Service llama mapper.toDto(saved) → obtiene un StudentDTO.
  6. Controller devuelve 201 Created + el DTO en formato JSON.

6. Spring Security con JWT

Hasta ahora cualquiera podía llamar a nuestra API. Vamos a protegerla usando Spring Security con JWT.

6.1 ¿Qué es un JWT?

Un JWT (JSON Web Token) es una cadena de texto firmada digitalmente que el servidor entrega al cliente tras un login correcto. A partir de ese momento, el cliente lo envía en cada petición y el servidor sabe quién es sin guardar ningún estado (es stateless).

Un JWT tiene 3 partes separadas por puntos, codificadas en Base64:

eyJhbGciOiJIUzI1NiJ9.eyJzdWIiOiJyb2dlciIsImV4cCI6MTcwMDB9.SflKxwRJSMeKKF2QT4fwpM
ParteContieneEjemplo
HeaderAlgoritmo de firma{"alg":"HS256","typ":"JWT"}
PayloadDatos del usuario (claims){"sub":"roger","exp":1700000000}
SignatureFirma con clave secretaHMAC-SHA256(header+payload, secret)
Atención

El payload está en Base64, NO cifrado. Cualquiera puede leerlo. Por eso nunca metas contraseñas ni datos sensibles dentro. La firma solo garantiza que nadie lo ha modificado.

6.2 Flujo de autenticación

  1. El usuario envía POST /api/auth/login con su usuario y contraseña.
  2. El servidor comprueba en la BD que la contraseña es correcta.
  3. Si lo es, genera un JWT con sus datos (usuario, rol, caducidad) y lo devuelve.
  4. El cliente guarda el token y lo envía en cada petición en la cabecera Authorization: Bearer <token>.
  5. En cada petición, un filtro en el servidor lee el token, comprueba la firma y, si es válido, permite el acceso.
Sesiones vs JWT (stateless)

Con sesiones, el servidor guarda en memoria un registro por cada usuario logueado. Con JWT no guarda nada: toda la información va dentro del token, firmada. Esto permite escalar horizontalmente (cualquier instancia del servidor puede validar cualquier token).

6.3 BCrypt: hash de contraseñas

Las contraseñas nunca se guardan en texto plano. Usamos BCrypt, un algoritmo que las convierte en un hash imposible de revertir:

passwordEncoder.encode("secret")
// → "$2a$10$N9qo8uLOickgx2ZMRZoMyeIjZAgcfl7p92ldGxad68LJZdL17lhWy"
  • Unidireccional: no se puede recuperar la contraseña original.
  • Con salt aleatorio: dos contraseñas iguales dan hashes diferentes.
  • Lento a propósito: dificulta ataques de fuerza bruta.

Para comparar la contraseña al hacer login:

passwordEncoder.matches("secret", hashGuardadoEnBD)
// → true o false

@Data @Builder @NoArgsConstructor @AllArgsConstructor
public class User implements UserDetails {

    @Id @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(unique = true, nullable = false) private String username;
    @Column(unique = true, nullable = false) private String email;
    @Column(nullable = false)                private String password;   // hash BCrypt

    @Enumerated(EnumType.STRING)
    private Role role;

    @Override
    public Collection<? extends GrantedAuthority> getAuthorities() {
        return List.of(new SimpleGrantedAuthority("ROLE_" + role.name()));
    }
    @Override public boolean isAccountNonExpired()     { return true; }
    @Override public boolean isAccountNonLocked()      { return true; }
    @Override public boolean isCredentialsNonExpired() { return true; }
    @Override public boolean isEnabled()               { return true; }
}

Paso 6 — JwtService

@Service
public class JwtService {

    @Value("${jwt.secret}")     private String secretKey;
    @Value("${jwt.expiration}") private long jwtExpiration;

    public String extractUsername(String token) {
        return extractClaim(token, Claims::getSubject);
    }

    public String generateToken(UserDetails u) {
        return Jwts.builder()
                .subject(u.getUsername())
                .issuedAt(new Date())
                .expiration(new Date(System.currentTimeMillis() + jwtExpiration))
                .signWith(getSigningKey())
                .compact();
    }

    public boolean isTokenValid(String token, UserDetails u) {
        String username = extractUsername(token);
        return username.equals(u.getUsername()) && !isTokenExpired(token);
    }

    private boolean isTokenExpired(String token) {
        return extractClaim(token, Claims::getExpiration).before(new Date());
    }

    private <T> T extractClaim(String token, Function<Claims, T> resolver) {
        Claims claims = Jwts.parser()
                .verifyWith(getSigningKey()).build()
                .parseSignedClaims(token).getPayload();
        return resolver.apply(claims);
    }

    private SecretKey getSigningKey() {
        byte[] keyBytes = Decoders.BASE64.decode(secretKey);
        return Keys.hmacShaKeyFor(keyBytes);
    }
}

Paso 7 — JwtFilter

@Component
@RequiredArgsConstructor
public class JwtFilter extends OncePerRequestFilter {

    private final JwtService jwtService;
    private final UserDetailsService userDetailsService;

    @Override
    protected void doFilterInternal(HttpServletRequest req,
                                    HttpServletResponse res,
                                    FilterChain chain)
            throws ServletException, IOException {

        String authHeader = req.getHeader("Authorization");
        if (authHeader == null || !authHeader.startsWith("Bearer ")) {
            chain.doFilter(req, res); return;
        }

        String jwt      = authHeader.substring(7);
        String username = jwtService.extractUsername(jwt);

        if (username != null &&
            SecurityContextHolder.getContext().getAuthentication() == null) {

            UserDetails user = userDetailsService.loadUserByUsername(username);
            if (jwtService.isTokenValid(jwt, user)) {
                var authToken = new UsernamePasswordAuthenticationToken(
                        user, null, user.getAuthorities());
                SecurityContextHolder.getContext().setAuthentication(authToken);
            }
        }
        chain.doFilter(req, res);
    }
}

Paso 9 — SecurityConfig

@Configuration
@EnableWebSecurity
@EnableMethodSecurity
@RequiredArgsConstructor
public class SecurityConfig {

    private final JwtFilter jwtFilter;
    private final AuthenticationProvider authProvider;

    @Bean
    public SecurityFilterChain filterChain(HttpSecurity http) throws Exception {
        http
          .csrf(AbstractHttpConfigurer::disable)
          .authorizeHttpRequests(auth -> auth
              .requestMatchers("/api/auth/**").permitAll()
              .anyRequest().authenticated()
          )
          .sessionManagement(s ->
              s.sessionCreationPolicy(SessionCreationPolicy.STATELESS))
          .authenticationProvider(authProvider)
          .addFilterBefore(jwtFilter, UsernamePasswordAuthenticationFilter.class);
        return http.build();
    }

    @Bean
    public AuthenticationManager authenticationManager(AuthenticationConfiguration cfg)
            throws Exception {
        return cfg.getAuthenticationManager();
    }
}

Paso 10 — AuthService

@Service
@RequiredArgsConstructor
public class AuthService {

    private final UserRepository userRepository;
    private final PasswordEncoder passwordEncoder;
    private final JwtService jwtService;
    private final AuthenticationManager authenticationManager;

    public AuthResponse register(RegisterRequest r) {
        if (userRepository.existsByUsername(r.getUsername()))
            throw new IllegalArgumentException("El usuario ya existe");

        User user = User.builder()
                .username(r.getUsername())
                .email(r.getEmail())
                .password(passwordEncoder.encode(r.getPassword()))
                .role(Role.USER)
                .build();

        userRepository.save(user);
        return new AuthResponse(jwtService.generateToken(user));
    }

    public AuthResponse login(LoginRequest r) {
        authenticationManager.authenticate(
            new UsernamePasswordAuthenticationToken(
                r.getUsername(), r.getPassword()));

        User user = userRepository.findByUsername(r.getUsername()).orElseThrow();
        return new AuthResponse(jwtService.generateToken(user));
    }
}

            .nota(dto.getNota())
